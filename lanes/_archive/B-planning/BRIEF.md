# Lane B · Planning and API

## Mission
SlackLine is a planning and recovery analysis tool for residential battery installers. It takes an installation plan plus a disruption (crew out, late shipment, slipped approval), finds the best recovery, and explains what is at risk and why.

Lane B turns the current plan plus disruptions into the best feasible recovery, validated, fast enough to re-plan live, and serves it over HTTP.

## Scope

### P0 (vertical slice first)
1. FastAPI app with every spec endpoint. First version serves `data/demo/tiny/expected/*.json`: match `POST /api/plans` on `scenario_id` + `mode` + `edits`, echo the request `revision`, return 501 for anything unrecorded. `scripts/export_openapi.py` writes `contracts/openapi.json`. Open this PR first. Lane C waits on the OpenAPI file.
2. `scripts/record_mocks.py` records every endpoint for tiny into `frontend/src/mocks/recorded/`. Rerun it after every API change.
3. CP-SAT strict model per SPEC section 7. Create only feasible (job, day, crew) variables. One cluster per crew-day. Capacity includes the cluster travel allowance. Cumulative inventory by date. Locks fixed. Replace the recorded strict response with the real planner.
4. Blocked jobs: a job with no legal (crew, day) option at all is `blocked` with reason codes and does not make strict infeasible. A job with options but none by its deadline makes strict infeasible.
5. Status: `optimal`, `feasible`, `infeasible`, `timeout_no_incumbent`, `invalid_input` stay distinct. Never return invalid assignments as success. Every plan goes through `validate_plan`.
6. Run solves off the event loop (`run_in_threadpool` or `asyncio.to_thread`).

### P1
7. Recovery mode with five lexicographic stages. The order differs from SPEC section 7 on purpose: see docs/DECISIONS.md, "Objective order". One total time budget. Stage-level status, value, bound, gap, and elapsed time.
8. Edits. Disruptions: remove crew-day, delay inventory, change ready date. Interventions: add crew-day, force include. Echo `revision`. Set `scenario_hash` with `app.contracts.hashing.scenario_hash(base, edits)`.
9. `POST /api/plans/compare`: stateless diff of `{before, after}`.
10. Baselines EDF and nearest-cluster-first via `algorithm` on `POST /api/plans`. Same validator.
11. `POST /api/plans/counterfactual`: stateless `{request, base, intervention}`. Force-include and add crew-day.

### P2
12. Value-aware objective from the value table. Deadline-and-travel-only policy revalued with the same table.
13. Solution hints from `current_plan` so recovery changes as few planned installs as possible.
14. Performance: 30 jobs under 5 s. Report 100-job timing in PROGRESS.md.

## Definition of done
- Every endpoint works on the tiny and standard fixtures.
- Tiny objectives match `data/demo/tiny/expected/` for strict, strict infeasible, recovery, and both counterfactuals.
- Timed-out, infeasible, and optimal are distinct in tests.
- Adding a crew-day never worsens a proven optimal objective (test).
- `make check-b` passes (planned target. Until it exists: `cd backend && uv run ruff check app/planning app/baselines app/compare app/api && uv run pytest -q tests/lane_b`).
